# Miru 角色系统及 HeyBuddy 的对应改造

## Miru 的角色如何进入模型

以下依据本机 Miru 源码，不启动应用或读取用户配置。角色定义、主对话编译和运行时状态是三个不同环节。

1. `model_library.py::get_active_soul_path()` 获取当前激活模型对应的角色文件；`character.py::_resolve_soul_path()` 使用该路径，异常时回到项目默认 soul.md。角色可以随当前模型选择改变，不是每轮由模型自行改人格。
2. `character.py::CharacterConfig._parse()` 按一级 Markdown 标题解析身份、性格、说话方式、背景、兴趣、情绪反应、关系阶段和提示词辅助字段。主回复没有额外的人格 Agent 调用。
3. `get_config()` 按用户和所选路径缓存配置；路径变化会失效，原路径内容改动需显式 reload_config()。它不通过修改时间自动热更新。
4. `prompt.py::_build_agent_system_prompt()` 先写时间、角色身份、内部用户标识和对外称呼，再固定顺序注入性格、说话方式、背景、兴趣、情绪反应、关系阶段；相关字段非空才加入。
5. `_load_agent_behavior()` 提供共享行为说明，之后补当前交谈模式、存在方式、短期连续性使用方法、记忆和工具说明、真实性反例。主对话不按每次输入关键词挑选一套情境剧本。
6. `core.py::_build_chat_context()` 汇总身份、核心记忆、归档索引、承诺、近期情绪、AttentionEngine 连续关注、屏幕观测及角色自身状态。`call_chat_agent()` 将该上下文追加到 system，再将真实聊天历史和当前消息交给 `_agent_iteration_openai()`。
7. `miru_emotion.py::format_for_context()` 将非中性心情写成“你现在的心情”，说明怎样自然影响语气。当前 get_relationship_stage() 固定返回“很亲近”，不是实时关系阶段；旧亲密/信任读取接口也返回满值。

## 自然感主要来自什么

soul.md 集中回答“我是谁、我在意什么、怎样对待眼前的人”。性格之后直接描述可听见的表现，例如担心时怎样问、感动时怎样变安静；“存在方式”再给出持续的交流动机。模型先得到交谈立场，再使用记忆和工具完成具体事情。

这种写法不依赖每条消息命中一个情境标签。普通问候和没有任务的分享也有位置；角色不必等用户拿出难题才出现。状态提供连续性，记忆提供具体内容，两者不能替代静态人格中清楚的说话方式。

自然程度也受模型、历史、固定亲近设定和动态上下文影响。此前一次无历史“你好”的真实测试不足以证明整体效果。

## HeyBuddy 已采用的结构

- 原生角色集中到一个中文 soul.md，一级标题解析成普通 profile 字段。Sherlock 内容依据本次会话确认的 Miru 式草稿重写。
- 先直接建立身份，再给性格、说话方式、背景、兴趣、情绪反应、相处方式和存在方式。少量表达参考也来自同一文件，不根据问题关键词更换人格材料。
- 共享模板补“当前交谈方式”“怎样使用记忆”“最近的状态”；角色标识和指纹移到末尾。状态服务读取同一个 soul 派生的身份和情绪反应。
- 四文件包只保留兼容路径；存在 soul 就不读取旧身份，损坏也不静默回退。默认包删除旧三份人格/行为/示例文件，避免两套权威内容。

## 与 Miru 保持的差异

角色仍由宿主 character_id 选择，不新增模型库或用户档案库。角色与自然的【真实与诚实】提醒合并为一条系统消息；动态记忆和状态继续用低信任 user 数据注入，注册表强制检查工具权限。程序架构说明不再作为“角色与执行边界”“宿主执行契约”注入模型。沿用有界状态、真实来源和有效期，不固定“很亲近”，不把模拟心情声明为真实意识。

不移植 AttentionEngine、屏幕感知、承诺副作用、主动消息或新后台循环，不使用全局代词替换。这些不是“单一角色源＋自然提示词”成立的必要条件。

实际路径、边界与测试见 [角色模块](modules/character.md)。本次验证编译结构和人格材料变化，是否更自然仍需后续固定条件的真实输出审阅。
