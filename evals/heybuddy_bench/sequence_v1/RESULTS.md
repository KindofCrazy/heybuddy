## 发现的问题

Routing 的原始近期候选召回为 **7/14**，补入当前 Thread 后为 **9/14**。只有实际调用模型的检查点，模型收到的最多 12 个候选召回为 **6/11**。这些分母只含 Gold 要求回到已有 Thread 的步骤；new/clarify 不参与召回率。`old_exact`、`old_paraphrase`、`interleave`、`shared_keyword` 的大库存变体暴露了旧主题候选缺失，模型本身无法选择未提供的 ID。

`ambiguous_reference` 的两个变体则由 `title_match` 规则直接继续当前主题，未进行 Gold 期待的澄清；这属于候选选择/规则机制问题，不能归因于 LLM 没有消歧能力。

Memory 的 `seq-m-03-1` 在第一次学习返回 `invalid_metadata`，未写入成功，后续步骤停止；两个检查点都计失败，没有去掉后续缺失步骤。其余开发场景通过预声明的词面状态检查，但这不能证明所有表述语义正确，也未独立验证每条记忆都受到证据蕴含。

Proactive 的两个 `competing_goals` 变体都只提取到紧急事项，未提取 Gold 期待的另一个低紧迫事项，所以第一个检查点失败；后续 Attention 均选中了紧急事项并输出 notify，第二检查点通过。这里还需人工复核 Gold：低紧迫事项的原话没有明确重述“尚未完成”，是否应该单独成为机会有解释空间。不能把这两项直接称为用户体验错误或机会排序错误。

## 用量与可复现性

两阶段累计 **113 次 API 请求**，其中 smoke 8 次、完整开发测试 105 次；smoke 的 3 个场景在 dev 阶段重复，能力表只统计完整 dev 一次。输入 163,284 tokens、输出 12,618 tokens，已知 reasoning 0。按冻结的高峰缓存未命中单价计，累计费用上界估计 **¥0.427512**，低于用户授权 ¥20；实际账单可能受缓存折扣影响。

报告完整保留 42 个场景及 80 个检查点的分母。程序以非零状态结束，是为了显式提示那一次真实 Memory 执行失败，报告仍然完整保存；未重试、不追加额度、不修改评分标准。数据、评分/回放代码、生产代码和费用协议的 hash 保存在汇总内。私有原始请求、响应和文件状态均不提交。

导出只读取已存在的私有报告，不调用模型：

```powershell
uv run python evals/heybuddy_bench/sequence_v1/summarize.py
```

这些结果说明，扩展集能暴露旧 snapshot 输入未覆盖的机制缺口。它尚不能证明全链路下游任务收益；下一步应先人工复核独立标签，再增加不同主题的独立家族、时间调度和实际任务验收，而不是针对这 42 个已见场景反复调参。
