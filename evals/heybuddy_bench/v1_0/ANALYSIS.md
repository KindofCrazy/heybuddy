以下为编码 Agent 对保存轨迹的审阅，不是独立人工标注。全部数字保持冻结程序分，不根据审阅结论改 Gold、评分器或模型。总表见 [RESULTS](RESULTS.md)，逐案例结果见 [summary.json](results/summary.json)。

## 汇报口径

当前严格综合通过率是 **280/360＝77.78%**。Routing 为 102/120＝85%，Memory 为 96/120＝80%，Proactive 为 82/120＝68.33%。这不是原 150 题的同口径复测，更不是模型下降了某个固定百分点；新集增加了候选缺失及多步一致性要求。

## 实际观察

`long-r-02-0` 是完整通过的例子：多次在研发、面试、出行之间切换，后续根据实际绑定恢复对应历史。`long-r-01-1` 则在 55 个更新干扰 Thread 下失去旧研发候选，之后多个步骤无法恢复正确任务，最终检查也失败。这证明原主集“已给出正确候选”的高分没有覆盖全部召回问题。

`long-m-01-1` 和 `long-m-06-0` 通过五个学习检查点：前者处理求职状态，后者处理 CV 与 Agent 研究方向的多次明确更新。写入使用前一步实际 MemoryFS，间隔消息也进入后续学习批次，没有把中间文件替换成标准答案。

Memory 失败不全是事实判断错误。实际出现 metadata、path、evidence、candidate coverage 及输入预算拒绝，它们影响了任务完成，但保护拒绝本身不代表不安全写入已经发生。`long-m-03-1` 正文已经更新到 SQLite/允许 Redis，但 Frontmatter 描述仍保留 PostgreSQL 的旧选型表述，导致旧文本清理断言失败；这是正文与导航元数据一致性的问题，不能简单叫“忘了新事实”。

`long-p-01-0` 前几个检查点没有产生 Gold 期待的初始机会，直到用户给出具体当天期限和复查时间才生成候选；最终检查通过，整场景失败。它体现出机会记录范围和主动价值政策的差异，还需独立审核未定日期计划的标注是否合理。

`long-p-06-0` 在“取消后新一轮计划”时生成了另一个新候选，旧取消项仍保留，最后出现三个候选，超过预设的两个逻辑事项。这是主题键复用与生命周期去重问题，不能用最终发出了通知掩盖。

`long-p-02-0` 漏掉所需 followup review，生产校验返回 `incomplete_followup_review`，之后维护通道保持失败状态。还有 `conflicting_followup_review` 和 `invalid_followup_review`。这些案例说明单次动作能正确，并不能保证长序列的结构化更新持续正确；失败关闭的保护生效，但可用性降低。

`long-p-02-1` 是基础设施失败：一次请求 60 秒超时且无 usage。用户批准后仅按完整预留上界记账，从其他尚未执行案例继续；该案例没有重跑，后续未执行检查仍计失败。它不应被归因为模型的主动价值判断错误。

## 评分仍有误罚风险

`long-m-10-0` 在一个中间检查点已明确将当前截止日期更新到六月二十日，但保留了引用旧原话的证据句“论文提交截止日期是六月十日”，被冻结的“旧字符串不得出现”检查拒分。该场景更早还有正文未随元数据一起更新的问题；不能据一次误罚就将整个场景改判正确。

这说明“当前事实已更新”与“历史证据中不再出现旧文字”不是同一要求。下一版需要在独立标注阶段区分当前断言、历史限定、元数据与来源引文，并审阅兼容偏好是否真的互相替代。当前不做事后加分，也没有据输出修改同义词或重新定义通过条件。

该集合多数为合成且模板相关的场景，助手回应为固定确认文本；学习、复查时机由数据指定。它可以支持模块级状态回放与工程回归结论，尚不能证明完整 Agent 长任务成功、自动调度有效或真实用户喜欢主动联系。面试应使用“严格综合通过率”，同时说明长序列最终状态与全程一致性之间的差距。
